# Каталог одежды и Telegram Mini App

Полный локальный сервис: администратор отправляет боту одну фотографию с названием в подписи; фотография сохраняется в MinIO, товар — в PostgreSQL и появляется в каталоге Next.js.

Стек: Next.js App Router / TypeScript, FastAPI, aiogram 3.x, SQLAlchemy, Alembic, PostgreSQL 17, MinIO, Nginx и Docker Compose.

## Быстрый запуск

Нужен запущенный Docker Desktop с Docker Compose. Из корня проекта:

```sh
python3 scripts/init_env.py
docker compose up -d --build
```

Открыть [http://localhost:8080](http://localhost:8080). По умолчанию каталог пустой; без Telegram-токена веб-каталог работает, а webhook возвращает 503 «Telegram не настроен».

Первая сборка MinIO компилирует официальные исходники и может занять несколько минут. Коммит закреплён в `infra/minio.Dockerfile`; облачные сервисы хранения не требуются. Python-зависимости зафиксированы в `backend/requirements.lock`, JavaScript — в `frontend/package-lock.json`.

## Подключение Telegram

1. Откройте [@BotFather](https://t.me/BotFather), выполните `/newbot` и создайте бота.
2. В локальном `.env` заполните `BOT_TOKEN` и `ADMIN_IDS` (числовые Telegram user ID через запятую). Свой ID можно узнать у [@userinfobot](https://t.me/userinfobot). Токен не отправляйте в чат и не коммитьте: `.env` игнорируется Git.
3. Откройте созданного бота в личном чате и нажмите Start. Это также позволит настроить персональное меню команд администратора.
4. Запустите временный HTTPS-туннель:

```sh
docker compose --profile tunnel up -d tunnel
docker compose logs tunnel
```

5. Скопируйте выданный адрес `https://….trycloudflare.com` в `PUBLIC_URL` в `.env`. `WEBHOOK_SECRET` уже сгенерирован командой инициализации.
6. Примените конфигурацию и зарегистрируйте webhook и кнопку Mini App:

```sh
docker compose up -d --force-recreate api
docker compose run --rm api python -m app.manage configure
docker compose run --rm api python -m app.manage webhook-info
```

После перезапуска туннеля адрес может измениться: обновите `PUBLIC_URL` и повторите шаг 6. Туннель предназначен для локальной разработки; PostgreSQL и MinIO не публикуются через него. На сервере замените туннель постоянным HTTPS-адресом, ведущим на gateway.

### Сценарий проверки

- Отправьте `/start`: бот ответит «У меня есть товар» и покажет «Открыть каталог».
- Для администратора доступны `/create_product` и кнопка «Создать товар».
- Отправьте одну фотографию с названием в подписи. Длина названия после удаления крайних пробелов — 1–255 символов; размер фото — до 10 МБ. Альбомы и изображения как документы не принимаются.
- После ответа «Товар … добавлен в каталог» откройте Mini App. В уже открытом каталоге данные обновляются при возврате в окно и каждые 10 секунд, пока окно видно.
- Пользователь вне `ADMIN_IDS` не может добавить товар.

Администратор может отправить корректное фото с подписью сразу, без команды. После «Создать товар» ожидание фотографии хранится в PostgreSQL и сохраняется при смене экземпляра: отдельное название без фото вызовет подсказку. Успешная загрузка или /start завершают этот режим. Обычные сообщения вне режима добавления получают приветствие с кнопкой Mini App. В памяти процессов состояние диалога не хранится.

## Данные и API

- `GET /api/products` → массив `{id, name, image_url, created_at}`, новые товары первыми. Ответ не кешируется.
- `GET /api/products/{id}/image` → оригинал JPEG из приватного bucket MinIO. Доступ к ключам хранилища браузеру не требуется.
- `GET /api/ready` → готовность PostgreSQL и MinIO, признак настройки Telegram.
- `POST /telegram/webhook` → Telegram updates с проверкой `X-Telegram-Bot-Api-Secret-Token`.
- Публичного endpoint создания товара нет. Прочие webhook-пути не маршрутизируются gateway.

Товары и обработанные updates хранятся в PostgreSQL; фотографии — в MinIO. SQL-транзакции и advisory locks защищают от одновременной обработки одинаковых сообщений. Ключ объекта детерминирован по исходному сообщению: повтор после сбоя между S3 и SQL не создаёт второй объект. Незавершённая обработка откатывается и возвращает ошибку для повторной доставки Telegram. Ответ с подтверждением возвращается только после коммита; Telegram не сообщает об успешности выполнения метода, возвращённого прямо в webhook-ответе.

Брошенный объект после сбоя S3→SQL остаётся под тем же ключом до повторной доставки; при повторе используется тот же объект. При окончательном отказе Telegram от повторов такой объект может остаться без записи и не отображается в каталоге.

## Масштабирование и сохранность

По умолчанию Compose поднимает два экземпляра API (с ботом) и два Next.js. Один образ используется всеми экземплярами своего сервиса. Nginx распределяет обращения через Docker DNS; привязка сессии к экземпляру не требуется. Данные и состояние диалогов не сохраняются в памяти приложений или на их локальных дисках.

```sh
docker compose up -d --scale api=3 --scale web=3
docker compose ps
```

Миграции выполняются отдельным одноразовым сервисом `migrate` до старта API. Bucket создаётся идемпотентно при запуске API. Healthchecks проверяют готовность; API отдаёт `X-Instance-ID` для диагностики распределения запросов.

PostgreSQL и MinIO — общие stateful-сервисы с именованными volumes. `docker compose down` сохраняет данные; `docker compose down -v` удаляет их. Репликация хранилищ и автоматическое переключение PostgreSQL в эту локальную конфигурацию не входят.

PostgreSQL (55432) и S3 (59000) привязаны только к loopback для локальной диагностики. В приложении bucket закрыт; учётные данные доступны только серверу.

## Демонстрационные товары

Шесть вещей из первоначального дизайна добавляются только явной командой:

```sh
docker compose run --rm api python -m app.manage seed
```

Повторное наполнение не создаёт дубли. Начальный статический прототип сохранён в `dist/`; прежняя публикация Sites остаётся отдельным демо и не подключена к новой базе.

## Тесты

Полный backend-набор с реальными PostgreSQL и MinIO, в отдельной базе `catalog_test` и временных buckets:

```sh
docker compose --profile test run --build --rm tests
```

Тесты проверяют права и валидацию, сохранение фотографии, чтение через другой экземпляр, конкурентные повторы webhook и повтор после сбоя S3→SQL. Внешняя загрузка из Telegram заменяется тестовым транспортом; живой Telegram требует настоящего бота и отдельной ручной проверки.

Frontend:

```sh
cd frontend
npm ci
npx playwright install chromium
npm test
npm run typecheck
npm run build
```

Можно использовать установленный Chrome, задав `PLAYWRIGHT_CHROME_PATH` путём к его исполняемому файлу. `E2E_BASE_URL=http://localhost:8080 npm test` проверяет собранный стек; без этой переменной Playwright сам запускает Next.js dev server.

Проверяются 375/768/1440 px, ошибки API и изображений, повторная загрузка, клавиатура, возврат фокуса, fullscreen-просмотр на телефоне, уменьшение движения, Telegram safe areas и BackButton.

## Локальная разработка

- `frontend/` — Next.js и браузерные тесты.
- `backend/app/` — API, aiogram, модель данных, сервис добавления и команды управления.
- `backend/migrations/` — миграции Alembic.
- `infra/` — Nginx и сборка MinIO.

Для frontend отдельно: `cd frontend && npm ci && npm run dev`; API по умолчанию ожидается на `127.0.0.1:8000`, адрес меняется через `API_INTERNAL_URL` перед запуском или сборкой. Основной поддерживаемый способ совместного запуска — Compose.
